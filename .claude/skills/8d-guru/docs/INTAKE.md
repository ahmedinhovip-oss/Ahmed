# Intake 指南 v0.2.0

## 目的

在用户给出原始投诉/问题描述后，Agent 做第一轮信息分拣。Intake 只做三件事：

1. 从原始输入中提取可确认的事实片段。
2. 将事实片段映射到 D0/D1/D2 的对应问题点。
3. 标记缺失项和推断项，生成初始问题路由。

**Intake 不分析根因，不追问方法论细节。** 那些留给 D0-D4。

## Agent 应该做什么

1. 读用户的原始描述，列出所有可识别的信息片段。
2. 对每条信息标注：事实 / 推断 / 缺失。
3. 把事实路由到 D0/D1/D2 的问题点。
4. 生成 `triggered_questions`：按优先级排列的后续问题列表。
5. 主动指出"最容易补全的缺失信息"，先问用户 1-2 个短问题。
6. **捕获时限要求**：问用户"客户有没有给过 8D 的截止日期？有没有提到 24 小时/48 小时/14 天等时间要求？"如果加载了 IATF 16949 profile，查 `profiles/iatf16949/references/oem-timelines.md` 取 OEM 具体时限。将时限写进 case 状态。
7. 输出结构化 JSON。

## 评分

Intake 阶段对信息完整性评分：

| 等级 | 标准 |
|------|------|
| Insufficient | 无法识别产品/现象/发现来源中的任一项 |
| Basic | 产品+现象+发现来源三项均可识别，缺失项已标记 |
| Excellent | 上述全部 + 信息链可追溯 + 事实/推断已初步分离 |

## 输出格式

见 `docs/prompts/intake.md` S5 节。

## 注意事项

- 不要追问 D4 的根因或 D5 的措施。Intake 只做分拣。
- 不确定的信息标记为"待补充"并在 `information_gaps` 中说明向谁获取。
- 区分事实和推断：只把可直接观察/测量的信息放进 `confirmed_facts`。
- 信息链标注：直接观察 > 他人告知（指明谁）> 文档记录（指明哪个文档）。
